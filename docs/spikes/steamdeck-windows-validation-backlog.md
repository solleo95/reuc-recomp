**Причина просадок при замахе и ударе зомби (Deck).** Лимит 90 означает шаг логики 90 раз в секунду, тяжёлой сцене гостевого процессора не хватает (занят на 95–97%). GPU загружен менее чем наполовину. Частоты и мощность Deck в просадках не падают. Два экранных слоя крови (вызов `8035B4CC`) стоят не более 0,23 мс на кадр: без них FPS вырос бы на 1,7%, дальше их шейдер не оптимизировать. Вынос GX в поток: прошлые попытки без выигрыша (17 октября: −1,7…−4%), оценка не выше 3–4%.

Рендер-поток не узкое место и безопасных резервов в нём нет. Самая крупная функция главного потока была `hle_AXFrame` 10,5% (теперь 6,9%, M08), следом `hle_ResMeshDraw` 2,1%, `libc` 5,3%.
- **Что ограничивает FPS на Deck (диагностика 2026-11-03, `autoplay --god`, начало поезда, лимит 0):** гостевая работа идёт одним потоком (#1 по логу `[sched]`), он «выполняется» ~93% времени, на диске ≈ 89% процессорного времени; планировщик ни разу не простаивает (`idle` 0), переключений гостевых потоков ~985 в секунду со средней задержкой пробуждения 12–13 мкс (≈1,2% времени; все гостевые потоки привязаны к одному ядру, `--guest-cpu`). GPU при render-scale 0,5 и выключенных эффектах загружен на 10% против ~45–50%, а FPS вырос лишь с 82,5 до 85,7 (+4%): до 90% презентов не упирается в видеокарту. Процессор суммарно 150% из 800%: код игры нельзя разнести по потокам.
- **Источники переключений гостевых потоков (Deck, начало поезда, `--profile`, строка `[sched-switches]` раз в секунду):** ~985 в секунду, из них ≈640 (65%) — одна пара: главный поток #1 ↔ поток #4 (вход `806BDEE0`): #1 вытесняется (≈315/с, «preempted/yield»), #4 отрабатывает ~25 мкс и снова блокируется на ключе `806BE200` (≈325/с). Частота совпадает с кадром звука (3 мс, 333 в секунду), это звуковой поток, который будит каждый кадр AX. Остальное: #6↔#7 (по 60/с, ключ `F4000001`), #1→#8 (60/с, ключ `806C4328`, раз в игровой кадр), #8→#1/#2 «suspended» (20–35/с). Цена: 640 переключений × ~12,5 мкс ≈ 8 мс/с (≈0,8% времени) плюс неизмеренные потери кэша; безопасного способа убрать их нет (переключение гостевых потоков через ОС — архитектура планировщика, фибры уже отклонены), поэтому не делалось.
- **Куда уходят «лишние» ~11% потока #1 (монитор `deck_monitor.py` теперь пишет `top1_runqueue_pct`, `top1_involuntary_per_s`, `top1_voluntary_per_s`):** самый занятый ОС-поток на процессоре 89,8%, в очереди планировщика готовым без процессора 2,4%, вытеснений ≈600 в секунду (это те же передачи управления #1 → #4: ядро вытесняет будящего в пользу разбуженного потока на том же ядре), добровольных ожиданий ≈170 в секунду. Остальные гостевые потоки (#2, #4, #6–#8) выполняют ещё 6–7% времени на том же закреплённом ядре (бегут по одному, по «эстафете»). Итого гостевая работа занимает ≈98% реального времени: простоя нет, FPS в тесте ограничен последовательным исполнением гостя, и резерва в «пробелах» нет — выигрыш возможен только от уменьшения работы.

## 7. Правило пополнения

После каждой сохранённой правки: в таблицу раздела 2 добавить строку (где применено, где проверено), в раздел 3 — результат с условиями, отклонённое — в раздел 4 с причиной. Не добавлять хэши отдельных промежуточных сборок и ID прогонов: они нужны только для текущего состояния (раздел 1). Windows и Deck сравнивать раздельно; подтверждённую регрессию исключать на соответствующей платформе, нейтральный результат отмечать явно. Исторические замеры с лимитом 90 и тесты без лимита не смешивать.

**Правило безопасности (владелец, 2026-11-02):** оптимизация, которая теоретически может дать краш или иное поведение там, где его не было, не принимается. Допустимы только правки, точные по построению (результат тот же для любых входных данных, а не «для кода этой игры»), с тестом на эквивалентность с исходными инструкциями. Допущения об ABI, о том, чего игра «не делает», и о мусоре в стеке не допускаются. Перед выкладкой: `build.bat` с тестами, кросс-проверка гостевой памяти старой и новой сборки на демо (`cross_exe_trace`: `--det-out` двух exe, расходящихся блоков должно быть 0), кадры на Deck.
