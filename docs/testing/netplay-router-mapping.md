# Автопроброс портов домашнего роутера

После **Multiplayer → Create host** лаунчер ищет UPnP IGD и открывает выбранный
порт (по умолчанию 27888) для TCP и UDP. В окне появляются состояние операции,
внешний IPv4 и кнопка копирования адреса. Партнёру нужны этот IP и тот же порт.
Клиент правил не создаёт. Прямой запуск `uc.exe --net-host` и тестовые harness
сами роутер не настраивают: владелец проброса — лаунчер.

Обнаружение, запросы и продление выполняются отдельным потоком. При запуске игры
лаунчер скрывается, остаётся фоновым процессом и следит за завершением именно
запущенной им игры. Он сохраняет правила через переход от TCP-лобби к игре.
После выхода игры, отмены лобби или ошибки запуска удаляются правила этого сеанса.
Отмена не ждёт ответа роутера в UI; повторное создание лобби доступно после очистки.
При закрытии лаунчера незавершённая очистка может ещё некоторое время работать
в скрытом процессе, ожидая сетевой вызов.

Запрашивается аренда на 600 секунд, продление — каждые 180 секунд. Роутер,
временно не ответивший при продлении, повторно опрашивается через 15 секунд;
существующие правила при таком сбое не удаляются. Роутер,
принимающий только постоянные правила (UPnP 725), получает правило без срока;
лаунчер показывает предупреждение. При штатном выходе оно также удаляется.
После аварии/принудительного завершения процесса временные правила истекут,
а постоянные правила с описанием `UC-…` может потребоваться удалить на роутере
вручную. Если роутер недоступен во время очистки, действует то же ограничение.

Чужой проброс не перезаписывается. Уже существующий постоянный включённый проброс
на тот же локальный адрес и порт используется без изменения и удаления.
Перед продлением/удалением своего правила проверяются адрес, порт и уникальное
описание сеанса. При конфликте выберите другой порт и сообщите его партнёру.
Если удалось создать только одно из TCP/UDP-правил, оно удаляется. Потеря ответа
на создание также проверяется: правило могло уже появиться на роутере.

Это UPnP домашнего роутера. CGNAT провайдера, дополнительный вышестоящий NAT,
relay-сервер, NAT-PMP/PCP и автоматические изменения Windows Firewall не реализованы.
Непубличный внешний IPv4 вызывает предупреждение. Успех UPnP подтверждает наличие
правил на роутере; достижимость извне требуется проверять с другой сетью.
Если UPnP отключён/недоступен, остаются LAN и ручной проброс. Доступ по сети
сохраняет ограничения текущего протокола: пароль и шифрование отсутствуют.

## Проверка

- `test_nat_mapping`: изолированный роутер проверяет оба протокола, владение,
  конфликт, частичный отказ, потерянный ответ Add, отмену во время добавления,
  восстановление исчезнувшей аренды, продление и завершение фонового потока.
- `uc_launcher --smoke <отдельный каталог>`: существующий UI smoke использует
  имитацию UPnP, проверяет лобби, готовность и сохранение проброса до handoff.
  Запросы к настоящему роутеру в smoke/CTest отсутствуют.
- `build/tests/test_nat_mapping.exe --router`: отдельная явная проверка настоящего
  роутера; создаёт/продлевает/удаляет TCP+UDP 39887. Код 3 означает недоступность
  проверки, подробная причина выводится в stderr. Чужие правила сохраняются.

MiniUPnPc 2.3.3 подключена только к лаунчеру, архив закреплён SHA256.
Лицензия поставляется в `licenses/miniupnpc/LICENSE`.

Проверка 2026-10-24: реальный UPnP-роутер принял временные TCP/UDP-правила на
39887, продление и удаление подтверждены повторным запросом
(`build/nat-router-probe.log`). Native UI smoke прошёл готовность и handoff
(`build/launcher-nat-smoke-verified.err.log`). Это не проверка доступности хоста
из другой внешней сети и не повторная оценка производительности rollback.
