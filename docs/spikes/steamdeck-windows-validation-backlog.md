**Deck:** первая сцена с зомби, лимит 90, настройки владельца.
- Blur 1 выборка на пиксель: GPU −16…−36% на тяжёлых полях движения, отличие от эталона 8 выборок на пиксель до 0,31 уровня из 255 на реальных кадрах.
- Проход Blur в покое 0,88 → ~0,50 мс (проход по тайлам 0,36 → 0,05 мс).
- Опрос SDL раз за кадр: медленных кадров (>16,7 мс) 6% → ~0,5%; игра на Deck с открытым контроллером 80 → 83 FPS.
- Список ключей на старте: ~1020 → 240 пайплайнов.

**Причина просадок при замахе и ударе зомби (Deck).** Лимит 90 означает шаг логики 90 раз в секунду, тяжёлой сцене гостевого процессора не хватает (занят на 95–97%). В секундах с просадкой гостевой поток тратит на кадр на 1,4 мс больше (10,05 → 11,44 мс), рост размазан по десяткам функций: декодирование вершин, запись FIFO, снимки состояния (`memcpy`), матрицы. GPU загружен менее чем наполовину. Частоты и мощность Deck в просадках не падают. Два экранных слоя крови (вызов `8035B4CC`) стоят не более 0,23 мс на кадр: без них FPS вырос бы на 1,7%, дальше их шейдер не оптимизировать. Вынос GX в поток: прошлые попытки без выигрыша (17 октября: −1,7…−4%), оценка не выше 3–4%.

## 4. Закрыто без внедрения (не повторять без новой причины)

- C01 чтение полей материала из SDK span; C03 `material_snapshot` по ссылке; C04 одна проверка диапазона в `psq_l/psq_st`; C06 прямой путь вершин; C07 целочисленные компоненты через умножение; C08 `PoolAllocator` для `DrawQueue`; C12 пропуск повторного сравнения uniforms; C13 добавление FIFO-байтов: нет прироста или хуже (регрессия Max/mean).
- C02 инварианты микшера аудио; C05 переобученный Linux PGO: без прироста.
- C09/C10 batch rollback отдельных листовых функций: заменены общим D08.
- C15 отдельное копирование четырёх байт: хуже. C17/C18: вошли только вместе в D11.
- C23 повторное использование выборок TEV, C25 индексирование текстур через дескрипторы, C24 точное copy вместо blit: нет выигрыша.
- C31 маска texcoord вершин, C33 кэш размеров атрибутов вершин (малые draw медленнее), C37 прямое копирование одинаковых участков (хуже минимумы), C40a/C40c/C41 варианты Blur (медленнее на реальных полях), C34 ThinLTO (+30 МБ памяти, прирост не доказан, на Windows ThinLTO уже включён).
- M02 флаг «transforms изменились» вместо memcmp 2 КБ в `hle_GXBegin` (живой путь; проверка `UC_GX_CACHE_VERIFY` расхождений не нашла): CPU гостя 33,20 → 33,26 с, wall в шуме (38–41 с), как и D05: выигрыша нет, откат.
- Оставшиеся цели профиля ниже порога A/B (≤1% каждая, итого не больше 2–3% при риске): `Vertices::decode` 1,7% (варианты C06/C07/C33 уже отклонены), запись в список FIFO (уже на быстром пути), `PSMTXConcat` уже векторизован, `call_indirect` 1% (промахи кэша по таблице `g_dense` ~7 МБ, не лечится дёшево), аллокации ~1,4% (стеки профилировщика мелкие, источник не найден; `hle_HitBufferConstruct` не выделяет память), двойное копирование списка в `GXEndDisplayList` 0,8%.
- Идеи транслятора (оставшиеся): `fcmp` + `cror` + `mfcr` + `rlwinm` (результат сравнения как целое число, ~270 мест) и прочие невыполненные свёртки CR; поле CR, живое после перехода, не сводится.
- Профилировщик: «вызывающий аллокации» по стекам глубиной 2–6 кадров ненадёжен (кадры без указателей), не опираться на него без `UC_CPU_SAMPLE_STACKS` и проверки кода.
- Слои крови (шейдер): верхняя оценка выигрыша 0,23 мс на кадр, не стоит риска.
- GX в отдельный поток: см. выше, ветки `gx-packet-worker`, `feat/gx-worker`, stash@{0}.

## 5. Как мерить и на что смотреть

- **Deck:** `ssh deck`, проверить, что игра не запущена; демо с зомби через `build/c23_compare.py` (`CANDIDATE=…`, `bench`/`capture`, `base`/`new`, приватные папки `~/uc-run/<case>/{base,new}` со своими данными и кэшами; в них копировать данные, не жёсткие ссылки). Нагрузка и просадки: `UC_TEST_REAL_PAD=1` в `scripts/uctest/deck.py` (иначе тест без контроллера, график кадров слишком ровный), `UC_CPU_SAMPLE=1` (+`UC_CPU_SAMPLE_STACKS=1`), `UC_DECK_MONITOR=1`. Сравнивать с лимитом 90 и без него отдельно.
- **ПК:** `py -3.13 -m uctest bench "<exe>|--game|S:\Games\Umbrella Chronicles\game|--per-pixel-lighting|--motion-blur|ultra|--bloom-strength|150|--game-hz|90" <второй exe> --demo zombie-firstscene --runs 3` (для opening и fight4 без `--game-hz`). Каждый вариант в своей папке рядом с `data` (копировать `dist` или `cmake --install … --prefix`); не копировать игровую папку целиком (56 ГБ текстур и extractor).
- **Картинку проверять кадром из игры**, не только временем: `uctest run perf --exe … --game-arg=--game --game-arg=<папка игры>` и открыть PNG. При включённом HDR захват не работает.
- **Ловушки сборки:** после возврата файлов из копии (`Copy-Item`) обновить даты изменения, иначе ninja оставит устаревшие результаты (так получилась серая картинка). `cmd /c` для `scripts\local.bat`+`env.bat` нужен для любой сборки из PowerShell; `build.bat` запускать по абсолютному пути.
- **Выход игры:** процесс не должен висеть после «log closed normally»; если висит, смотреть дочерние процессы (`nvngx_update.exe`).
- Диагностика SDL/Deck-контроллера: драйвер Deck HIDAPI шлёт служебные отчёты (~8 мс) каждые 200 опросов; системный SDL 3.4, не встроенный 3.2.0.

## 6. Открыто

- Гостевой процессор в замахе/ударе (+1,4 мс на кадр): адаптивный лимит (держать шаг на достижимой скорости), остаток микрооптимизаций CPU (M01 сделан, M02 отклонён; см. раздел 4: каждая из оставшихся целей ≤1–2%), 60 Гц логика + интерполяция (ветка `experiment/fps-interpolation`).
- Сид для глав 2–4 (нужны сохранения с открытыми главами); старый сид содержал 9 состояний смешивания, перенесены 9 ключей-носителей.
- DX11/DX12 с этими правками; отдельный A/B для D10/D11 на Windows; Windows PGO под новые функции.
- Выход игры на Deck не проверялся на аналог зависания.

## 7. Правило пополнения

После каждой сохранённой правки: в таблицу раздела 2 добавить строку (где применено, где проверено), в раздел 3 — результат с условиями, отклонённое — в раздел 4 с причиной. Не добавлять хэши отдельных промежуточных сборок и ID прогонов: они нужны только для текущего состояния (раздел 1). Windows и Deck сравнивать раздельно; подтверждённую регрессию исключать на соответствующей платформе, нейтральный результат отмечать явно. Исторические замеры с лимитом 90 и тесты без лимита не смешивать.

**Правило безопасности (владелец, 2026-11-02):** оптимизация, которая теоретически может дать краш или иное поведение там, где его не было, не принимается. Допустимы только правки, точные по построению (результат тот же для любых входных данных, а не «для кода этой игры»), с тестом на эквивалентность с исходными инструкциями. Допущения об ABI, о том, чего игра «не делает», и о мусоре в стеке не допускаются. Перед выкладкой: `build.bat` с тестами, кросс-проверка гостевой памяти старой и новой сборки на демо (`cross_exe_trace`: `--det-out` двух exe, расходящихся блоков должно быть 0), кадры на Deck.
