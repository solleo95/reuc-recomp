# Выпуск Windows-клиента

Запустите `build-release.bat` из корня проекта. Нужны обычные инструменты сборки
проекта и Python 3.10+. Введите версию строго `X.Y.Z`, например `0.0.1`.
Каждая часть — число от 0 до 65535, без ведущих нулей.

Скрипт выполняет `build.bat --no-install`: актуальная трансляция, сборка и тесты.
Тесты запускаются параллельно по числу логических процессоров Windows
(`NUMBER_OF_PROCESSORS`). Тесты с `RUN_SERIAL` выполняются отдельно.
Для ручного ограничения задайте `CTEST_PARALLEL_LEVEL` перед запуском сборки.
После успешной сборки выполняется отдельная установка CMake в новый временный
каталог. Старое содержимое `dist` в релиз не попадает. Установленная игра в
`UC_INSTALL_DIR` не изменяется.

Результат:

- `dist-release/` — чистый клиент с `uc.exe`, `uc_launcher.exe`, `uc_updater.exe`,
  необходимыми DLL, ресурсами и `release.json`;
- `UC-Windows-0.0.1.zip` в корне проекта — содержимое клиента непосредственно
  в корне ZIP, без дополнительной папки.

`release.json` содержит версию, размеры и SHA-256 каждого управляемого файла,
а также DLL для автономной копии обновлятора. Перед публикацией результата ZIP
проходит тот же нативный валидатор, который проверяет скачанное обновление.
Существующий ZIP этой версии не перезаписывается. При ошибке публикации предыдущий
`dist-release` восстанавливается; при невозможности восстановления путь к копии
выводится в ошибке. Служебные каталоги `.release-build-*` не добавляются в Git.

Для запуска из терминала с уже настроенным окружением сборки:

```text
python -I scripts/build_release.py --version 0.0.1
```

## GitHub Release

1. Создайте релиз в [solleo95/reuc-recomp](https://github.com/solleo95/reuc-recomp/releases).
2. Укажите тег `0.0.1` или `v0.0.1`. Версия тега должна совпадать с `release.json`.
3. Прикрепите `UC-Windows-0.0.1.zip`; имя должно точно соответствовать версии.
4. Опубликуйте обычный релиз и назначьте его **Latest**. Draft и prerelease
   лаунчер игнорирует. Описание релиза показывается обычным текстом.

Репозиторий и релиз должны быть публичными. Лаунчер обращается к GitHub API
без токенов; проверяет SHA-256 asset из поля `digest`. Пока digest отсутствует,
установка не предлагается. ZIP загружается только с GitHub и разрешённых
доменов его хранилища релизов.

## Первая установка и обновление

Первую версию с автообновлением распакуйте вручную в отдельную доступную для
записи папку. Обычная dev-сборка без корректного `release.json` автоматически
не обновляется. Не переносите манифест отдельно от соответствующих ему файлов.

При запуске лаунчер один раз проверяет Latest. Для новой версии предлагает
«Обновить» или «Позже». Ошибка сети не мешает игре. Перед обновлением закройте
другие экземпляры игры и лаунчера. Загрузку можно отменить.

После проверки ZIP служебный обновлятор сообщает готовность, лаунчер закрывается,
файлы заменяются и лаунчер запускается вновь. До подтверждения готовности окна
и фиксации обновления новая версия не записывает настройки. При ошибке установки
или запуска обновлятор восстанавливает предыдущие управляемые файлы.

Сохраняются `config.json` и его служебные файлы, `saves/`, `mods/`, `textures/`,
`game/`, `debug/`, `logs/`, профили CPU, пользовательская `nvngx_dlssnr.dll`,
кэши `data/pipeline_keys.bin`, `data/pipeline_cache.bin` и временные файлы кэша.
Неизвестные файлы сохраняются; конфликт нового пути с неизвестным файлом
останавливает обновление. `mods-examples/`, SDK и штатные ресурсы обновляются.

Ручная распаковка другого ZIP поверх клиента не выполняет этот алгоритм
сохранения данных и отката. Для следующих версий используйте лаунчер.

## Восстановление

Журнал, резервные копии и автономный обновлятор находятся в
`.uc-update/<идентификатор>/`. При следующем запуске лаунчер проверяет прерванную
операцию до работы с настройками и запускает восстановление. Прямой запуск игры
при незавершённой транзакции блокируется.

Если штатный лаунчер повреждён, запустите
`.uc-update/<идентификатор>/recovery/uc_updater.exe` без аргументов и подтвердите
восстановление. Окно ошибки показывает путь операции. Не удаляйте её `backup/`
и журналы до успешного восстановления. Завершённые операции очищаются при
следующем обычном запуске лаунчера.

Логи лаунчера — `logs/`; ход транзакции — `journal.json` и `journal.log` внутри
каталога операции. Проверка запуска подтверждает готовность лаунчера, а не
отсутствие любых будущих ошибок игры. Отказ накопителя или потерю его данных
программный откат исправить не может.
