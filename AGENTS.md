# Agents

- Optimization state (what is installed on Deck and Windows, which change applies where, closed candidates, how to measure, open items): `docs/spikes/steamdeck-windows-validation-backlog.md`. Read it first and keep it current (its section 7 says how); old logs live in `docs/spikes/archive/` and are history only.

- Live testing of `uc.exe`: use the harness, never system input. Skill: `.claude/skills/uc-test/SKILL.md`; protocol: `docs/testing/test-server.md`.
- Never run any test, bench, demo or smoke run fullscreen (no `--window-mode borderless|exclusive`, no desktop-sized windows): the harness forces a 1280x720 window (`docs/testing/test-server.md`); never lift that unless the owner asks in the same message. For a higher internal resolution use `--game-arg=--render-scale`.
- Build: `build.bat --no-install` (translator, build, tests, stages `dist`). Tests only: `ctest --test-dir build --output-on-failure`. `build.bat` runs only the tests whose exe, command or data files (`tests` data and fixtures, `tools`, `modding`, `mods-examples`) changed since they last passed (per-test keys in `build/tests.state.json`, `scripts/tests-run.ps1`; delete the file to run all). Failed tests stay pending. The tests run on a hidden Windows desktop (`scripts/hidden-desktop.ps1`, also `scripts/ctest-hidden.ps1 <ctest args>`), so their windows never appear over what the user is doing; `UC_TESTS_VISIBLE=1` runs them on the real desktop to watch one.
- Run a scenario: `cd scripts && python -m uctest run train_gameplay --speed 8`.
- Never run the game against the real saves; the harness copies them into `build/autotest/<run>/saves`.
- Every test, bench and demo runs the game unlocked (`--fps-limit 0`, as a player does); a limit only by an explicit `--game-arg=--fps-limit --game-arg=N`. Deterministic runs (demo/bench) use a virtual clock, so the heavy fight then plays slower than real time on screen: that is wall time per fixed work, not a bug.
- Performance changes: judge them ONLY with the protocol in `docs/testing/performance-measurement.md` (Deck: `python scripts/linux/measure.py BEFORE AFTER`: one run before, remembered per binary, one run after; it judges the guest instruction count, exact to 0.002%, and escalates to `--full` over several code layouts when a time claim is needed). A wall-clock A/B of two builds, a single FPS run, a live `fight`/`perf` run and the share of a function in a profile are NOT evidence: code layout alone moves a build by +-1% and has produced false losses and false gains. Never reject a change because one bench of two builds came out slower. `deck_bench.py` and `uctest bench` are for looking, not for deciding. The same protocol is planned for Windows (document, section Windows). Record a demo with `python -m uctest demo record <name>` and again after a change that alters what the guest can see (`demo check <name>` proves replay == recording). Details: `.claude/skills/uc-test/SKILL.md`.
