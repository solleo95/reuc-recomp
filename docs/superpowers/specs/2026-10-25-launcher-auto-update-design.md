# Автообновление клиента UC через GitHub Releases

Дата: 2026-10-25
Статус: дизайн согласован пользователем 2026-10-25; составляется план реализации.
Выбранный пользователем подход: полный ZIP, отдельный обновлятор, откат.
Репозиторий релизов: https://github.com/solleo95/reuc-recomp
Пользователь подтвердил: к выпуску репозиторий будет публичным.

## Цель и сценарий

Автор запускает build-release.bat, вводит версию (например, 0.0.1),
получает свежий клиент в dist-release и архив UC-Windows-0.0.1.zip.
Затем вручную создаёт GitHub Release с соответствующим тегом и прикрепляет ZIP.
Установленный клиент при запуске обнаруживает новую версию, предлагает обновиться,
скачивает и проверяет пакет, закрывает лаунчер, устанавливает пакет отдельным
процессом и снова открывает лаунчер. Пользовательские данные сохраняются.

## Существующая архитектура и границы

- Лаунчер: native Windows C++20, SDL3, Dear ImGui; существующий цикл UI и
  фоновая обработка запросов. Фоновая проверка не блокирует интерфейс.
- build.bat --no-install собирает проект, выполняет тесты и подготавливает dist.
  dist не очищается и содержит пользовательские/экспериментальные файлы.
  Использовать его содержимое как источник ZIP нельзя.
- CMake install уже описывает клиент: EXE, DLL, ресурсы лаунчера, шейдеры,
  компоненты апскейлеров, документацию, SDK, примеры модов и лицензии.
- Оригинальные игровые данные нужны существующему клиенту отдельно. Релиз клиента
  их не упаковывает и обновлятор их не изменяет.
- Настройки, сохранения, моды, текстуры и диагностические файлы существуют рядом
  с программой. Замена всего каталога установки целиком недопустима.
- В рабочем дереве уже есть изменения, включая лаунчер, сборку и диагностику.
  Реализация должна учитывать их; чужие изменения не откатывать и не коммитить.

## Подходы и выбор

1. Полный ZIP и отдельный обновлятор: простой выпуск одного архива,
   единый проверяемый пакет и откат. Недостаток: загрузка всего клиента.
2. Манифест отдельных загрузок: экономия трафика, но больше сетевых операций,
   состояний публикации и вариантов частичного обновления.

Пользователь выбрал первый вариант. Манифест внутри полного ZIP нужен для
контроля состава и удаления устаревших файлов; отдельные загрузки не реализуются.

## Предлагаемые решения автора дизайна

Следующие детали предложены исполнителем и входят в согласуемый дизайн:
- Один канал стабильных релизов, версии из трёх числовых компонентов.
- Пакет содержит учёт версии и список управляемых файлов с размерами и SHA-256.
- Обновлятор — отдельный native Windows EXE; переносимая установка без службы.
- Проверка целостности ZIP по SHA-256 из GitHub API; отсутствие/несовпадение
  контрольной суммы запрещает установку, сохраняя работающий клиент.
- Восстановление опирается на журнал операции и резервные копии.
- Кнопка «Позже» откладывает предложение до следующего запуска.
- Поддержка скачивания по частям, prerelease-каналов и подписи пакетов отдельным
  ключом вне объёма этой версии.

## Сборка релиза

1. build-release.bat работает относительно своей директории; пути с пробелами
   и кириллицей корректны. Ввод версии проверяется до передачи другим процессам.
2. Формат ввода: X.Y.Z, неотрицательные десятичные целые, без ведущих нулей
   кроме самого нуля. Ограничить длину/диапазон компонентов, исключить переполнение.
   Тег релиза допускает X.Y.Z или vX.Y.Z; имя ZIP всегда UC-Windows-X.Y.Z.zip.
3. Использовать существующий процесс сборки и тестов с --no-install. При любой
   ошибке прекращать выпуск; не оставлять новый ZIP под итоговым именем.
4. Из актуальной сборки выполнить чистое CMake staging в отдельную временную
   release-директорию. Не копировать dist и пользовательскую установленную игру.
5. Сформировать release.json: версия, версия формата, список относительных путей,
   размеры и SHA-256 файлов клиента. Сам release.json исключить из собственного
   списка хешей, но учитывать как управляемый файл при установке/откате.
6. Проверить состав: обязательны игра, лаунчер, обновлятор и нужные runtime-файлы.
   Не включать пользовательские данные, тестовые EXE, логи, секреты, исходные
   игровые данные. Корень ZIP непосредственно содержит файлы клиента.
7. После успешной упаковки и проверки опубликовать локально dist-release и ZIP
   рядом с ним в корне проекта. Существующий результат той же версии не
   перезаписывать молча: явное подтверждение в .bat или выход с понятной ошибкой.
   Очистка разрешена только для проверенных собственных staging-путей.
8. Вывести путь ZIP и напоминание о совпадении версии/тега/имени вложения.
   GitHub-публикация остаётся ручной. Тесты упаковки используют фиктивные файлы.

## Поиск обновления и интерфейс

- Источник: официальный GitHub REST API указанного публичного репозитория,
  endpoint latest release. Автор выпуска помечает нужный стабильный релиз Latest.
- Игнорировать draft/prerelease. Проверять корректность ответа, тег, нужное
  вложение с точным именем и состояние загрузки; сравнивать версии численно.
  Дата релиза не определяет, новее ли он локальной версии.
- Локальная версия берётся из release.json. Для обычной dev-сборки без валидных
  release-метаданных автоустановка отключена; ручная установка первой версии
  с этим механизмом обеспечивает дальнейшие обновления.
- Один фоновый запрос за запуск, ограниченные таймауты, размер ответа и число
  перенаправлений. Ошибка сети, 404 или rate limit не мешают запуску игры.
- Модальное окно: текущая/новая версия, описание релиза обычным текстом,
  размер загрузки, «Обновить» и «Позже». Во время загрузки — прогресс и отмена.
  Не исполнять HTML из GitHub и не интерпретировать описание как команды.
- UI владеет состоянием; фоновый поток возвращает типизированный результат.
  Закрытие/отмена прекращают работу или игнорируют устаревший результат.
  Повторное нажатие не запускает параллельное скачивание/установку.
- Во время подготовки обновления запуск игры блокируется. Если игра уже работает,
  предложить закрыть её и повторить установку; принудительно не завершать.
- Ошибка проверки/скачивания оставляет текущую версию работоспособной и позволяет
  повторить попытку. Нет сети — обычный запуск клиента.

## Проверка загрузки и файлов

- Только HTTPS с обычной проверкой сертификата; начальный URL вложения берётся
  из API ожидаемого репозитория. Разрешать только необходимые GitHub/CDN
  перенаправления по HTTPS, с ограничением числа переходов.
- Проверять фактический размер и SHA-256 ZIP до распаковки. Если GitHub не дал
  пригодный digest, показывать ошибку установки и ссылку на страницу релиза.
- Распаковывать в изолированный staging, не поверх рабочей установки.
  Установить ограничения размера ZIP, числа файлов, суммарного распакованного
  размера; конкретные значения привязать к размеру штатного пакета.
- Отклонять абсолютные/UNC-пути, выход через .., ADS, ссылки и reparse points,
  зарезервированные Windows-имена, дубликаты с учётом регистра и нормализации,
  конфликт файл/каталог и любые пути в защищённые пользовательские области.
  Проверять также существующие компоненты путей назначения на reparse points.
- Проверять формат/версию манифеста, совпадение версии с релизом, наличие всех
  перечисленных файлов, их хеши/размеры и отсутствие лишних файлов в ZIP.
- GitHub TLS + digest защищают целостность доставки. Компрометация аккаунта
  издателя остаётся риском; отдельная инфраструктура подписания не добавляется.

## Какие файлы можно менять

- Источник нового состава — проверенный release.json из ZIP; старого состава —
  локальный манифест ранее установленного релиза.
- Обновлять только управляемые файлы клиента. Файлы, исчезнувшие из новой версии,
  удалять только если старый манифест объявлял их управляемыми.
- Локальный манифест также считать недоверенным: те же ограничения путей,
  защищённых областей и допустимой структуры.
- Неизвестные файлы сохранять. Если новый управляемый путь занят существующим
  неуправляемым файлом, остановить установку с объяснением конфликта.
- Защищённые области: config.json, saves/, mods/ и их кэши, textures/,
  оригинальные игровые данные, debug/, logs/, пользовательские профили CPU
  и прочие runtime-настройки. Полный список конкретных имён установить по коду
  перед реализацией; тесты фиксируют запрет записи даже при поддельном манифесте.
- Поставляемые примеры в mods-examples/ и SDK обновляются как файлы клиента.
  Рабочие пользовательские моды в mods/ сохраняются.

## Обновлятор, блокировки и откат

1. Лаунчер готовит и проверяет staging, запускает копию обновлятора в служебной
   директории этой установки. Копия позволяет обновить штатный EXE обновлятора.
   Передать параметры безопасным API создания процесса, без командной оболочки.
2. Обновлятор повторно проверяет пакет/пути и получает эксклюзивную блокировку
   установки. Межпроцессная координация блокирует другие лаунчеры и запуск игры.
   Учитывать игру, запущенную другим экземпляром/напрямую, и занятые DLL/EXE:
   при невозможности безопасной замены выйти до изменений либо откатить их.
3. Проверить свободное место под staging, резервные копии и журнал, права записи,
   допустимость целевых путей. Установка в недоступную директорию завершается
   понятной ошибкой; автоматического повышения привилегий нет.
4. Обновлятор сообщает лаунчеру готовность; только затем лаунчер штатно закрывается.
   Обновлятор ждёт фактического завершения процесса по process handle с таймаутом.
   Если подготовка/запуск helper не удались, лаунчер остаётся открытым.
5. В пределах одного тома сохранить резервные копии заменяемых/удаляемых файлов.
   До мутаций записать устойчивый журнал: пути, предыдущие/новые файлы,
   намерение и завершение каждого шага. Изменения повторяемы при восстановлении.
6. Применить новый состав; новые файлы также записываются в журнал для удаления
   при откате. Метаданные установленной версии заменить после файлов клиента.
7. Запустить новый лаунчер в правильной рабочей директории. Он подтверждает
   успешную минимальную инициализацию обновлятору через локальный канал с
   идентификатором операции; проверка не ждёт GitHub или запуска игры.
8. После подтверждения зафиксировать успех, снять блокировку и убрать резервную
   копию. Откат гарантирует восстановление файлов при сбое установки, но не
   обнаружение любых будущих ошибок игры.
9. Если замена или запуск/подтверждение не удались: остановить созданный новый
   процесс при необходимости, восстановить прежние файлы/метаданные, удалить
   добавленные текущей транзакцией файлы, перезапустить прежний лаунчер.
10. При аварии/отключении питания журнал и backup остаются. До обычного старта
    лаунчер обнаруживает незавершённую транзакцию и запускает восстановление.
    Если штатный EXE отсутствует/повреждён, сохранённая служебная копия
    обновлятора предоставляет ручной запуск восстановления. Не обещать
    автоматический запуск восстановления при старте Windows.
11. Сбой самого отката не очищает резервную копию и журнал. Показать точный путь
    восстановления и диагностики; не сообщать об успехе и не продолжать смешанную
    установку как исправную. Повторное восстановление безопасно.

Применение выполняется без консольного окна. Служебный обновлятор должен иметь
минимальное окно состояния/ошибки, чтобы закрытие лаунчера не скрывало результат.
Проверку незавершённого обновления выполнять до записи настроек новой версией.

## Проверки реализации

- Версии: 0.0.9 < 0.0.10, v-префикс, некорректные версии, переполнение,
  одинаковая/старая версия, prerelease, отсутствие нужного ZIP.
- GitHub/сеть через тестовый transport: ошибка, таймаут, rate limit, отмена,
  несоответствие размера/хеша и отсутствие digest; устаревшие ответы.
- ZIP/манифест: обход каталога, ADS, ссылки, регистр, лишний/пропущенный файл,
  защищённые пути, конфликт неизвестного файла, лимиты распаковки.
- Транзакция на фиктивной установке: штатное обновление, удаление старого
  управляемого файла, неизменность пользовательских данных, ошибка на каждом
  этапе, занятый файл, сбой перезапуска и повторное восстановление из журнала.
- Блокировка: две установки одновременно, игра работает, повторное нажатие,
  отмена/закрытие лаунчера и handshake с обновлятором.
- Пакет: чистый staging без загрязнений dist; ошибка сборки не создаёт финальный
  ZIP; версия/имена/состав совпадают; пути с пробелами и кириллицей.
- Проверить native UI и реальный перезапуск на изолированной копии, с фиктивными
  релизами, без записи в пользовательскую установленную игру.
- Любые запуски uc.exe — только через существующий uctest harness, оконно,
  с копиями сохранений. Сценарий обновления сам по себе не требует запуска игры.
- Запустить необходимые целевые тесты и штатную сборку/тесты проекта перед
  заявлением готовности. Невыполненные проверки явно перечислить.

## Объём и свобода реализации

Это изменение сборки, лаунчера и отдельного процесса установки, со своими
тестами транзакции. Существующие UI-компоненты, JSON и тестовые инструменты
переиспользуются; новых сервисов, авто-публикации и GitHub-токенов в клиенте нет.

Исполнителю остаются: разбиение C++ модулей, механизм IPC/блокировки,
конкретные лимиты, инструмент ZIP с необходимой безопасной валидацией,
HTTP на Windows и точные имена служебных файлов. Предпочтительны существующие
зависимости и Windows API; крупный фреймворк автообновлений не добавлять.

Следующий шаг после согласования документа — план реализации.
Коммиты и публикация этим согласованием не разрешаются.

## Уточнение оформления — 26 октября 2026

После просмотра обоих окон пользователь подтвердил графитовое оформление
отдельного обновлятора и поручил улучшить модальное окно лаунчера.
Сохраняем существующий стиль: светлый текст, графитовый фон, бордовый акцент.
В модальном окне выделяем основное действие и отделяем примечания к релизу.
Служебное окно показывает заголовок, неопределённый индикатор работы и пояснение
об автоматическом перезапуске/откате. Проценты установки не имитируем.

Для чёткости при 125% и переносе между мониторами служебный EXE объявляет
PerMonitorV2 через манифест; WM_DPICHANGED обновляет размеры и шрифты.
Используем Win32/GDI без новой зависимости от SDL в служебном обновляторе.
Проверки: реальные окна, масштабирование клиентской области 100/125/150/200%,
RU/EN служебного окна, все 13 языков и действия модального окна.
